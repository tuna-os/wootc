# VM-first experiments, 2026-09-26

Goal: someone with little technical knowledge can reach a useful Linux desktop with their data,
keeps their work, and can choose native boot later.
[ADR 0004](../adr/0004-restore-vm-first-product.md) defines that journey.
A distro logo, a QEMU process, or a Linux console alone does not meet it.

## Candidate paths

| Candidate | First-run work on the PC | Benefit to test | Cost or risk to test |
|---|---|---|---|
| A: current Alpine RAM builder | Pull OCI image, unpack and install in a 2 GiB helper VM, then launch desktop | Existing prototype, small helper download | Rootfs and image-store memory budget; startup gaps; duplicate work |
| B: helper with disk-backed scratch | Fetch verified OCI closure in Windows, provision persistent raw disk inside a helper VM | One provisioner, arbitrary approved bootc image, low-memory preparation | Time and scratch space on an old disk; helper lifecycle and image verification |
| C: prebuilt persistent image | Download verified compressed raw disk, extract, personalize, resize, launch | Move costly image assembly to release CI; fewer first-run stages | Download size; release/storage cost; identity reset; secure personalization; later update/native compatibility |
| D: native deployer first | Reboot out of Windows for installation | Existing full-cycle evidence | Fails the required VM-first journey; explicit fallback only |

Candidate C is the leading UX hypothesis, not a measured winner.
Candidate B remains necessary for custom images and may win on download reuse.
Both must preserve the exact installed disk across VM and native use.
Do not ship a disposable trial that discards the person's setup later.

## Experiment 1: current desktop image sizes

Fetched the current Linux/amd64 registry manifests on 2026-09-26.
The measurements come from layer descriptors. They do not time a download or measure an installed disk.
Digests pin the observation even if the tags move.

| Image | Compressed layer bytes | Layers | Observation |
|---|---:|---:|---|
| `ghcr.io/projectbluefin/bluefin:lts` | 2,870,798,983 | 128 | Compressed payload alone exceeds the prototype's 2 GiB guest allocation |
| `ghcr.io/tuna-os/yellowfin:gnome` | 1,793,371,955 | 65 | Little headroom before rootfs, runtime, unpacked layers, and VFS copies |

[Exact digests and measurements](evidence/2026-09-26-vm-first/oci-sizes.json).
The current builder keeps its writable rootfs and VFS image store in RAM.
It mounts `/var/tmp` as a tmpfs; it does not provide a disk-backed image store.
These numbers do not support a claim that desktop images fit this 2 GiB builder.
They do not measure peak RAM or prove that every image fails at the same point.

Decision: prototype B with explicit scratch storage. Do not make A depend on a large allocation of host RAM.
Older PCs are the priority, not an afterthought to the provisioner.

## Experiment 2: build the existing helper

Ran the actual `payload/builder/build-builder.sh` with Alpine 3.21.
It completed successfully on the shared development host.

| Artifact | Bytes |
|---|---:|
| `builder-vmlinuz` | 11,731,968 |
| `builder-initramfs.img` | 90,463,252 |

[Hashes and build record](evidence/2026-09-26-vm-first/builder-build.json).
This proves that the build can produce the helper artifacts.
It does not prove that the helper boots, has network/storage drivers, or installs a target.
The local build took 171.01 seconds, but shared-host load and caches prevent a product-speed claim.

A startup probe booted these artifacts under QEMU TCG on Linux, with 2 GiB RAM and one CPU.
The target was a sparse raw file of 20 GiB.
The guest printed `FAIL: target disk /dev/vda not present` and powered off.
QEMU exited zero. The preallocated disk still existed, and IPC was empty.

This reproduces the false-success path corrected by PR #411.
It also exposes a startup gap: the current init does not load the VirtIO drivers.
The run proves a startup failure, not Windows acceleration or desktop performance.

The follow-up passed checks at startup with the same 2 GiB allocation.
It loaded VirtIO drivers, used DHCP, and added a scratch disk of 8 GiB.
The guest observed `/dev/vda` and `/dev/vdb`, obtained a DHCP lease, and mounted ext4.
Both `/var/lib/containers` and `/var/tmp` resolved to the scratch disk through `findmnt`.
Serial and IPC both carried `WOOTC_DISK_BACKED_PROBE_READY` before clean poweroff.

[Probe results](evidence/2026-09-26-vm-first/disk-backed-probe.json),
[serial evidence](evidence/2026-09-26-vm-first/disk-backed-serial.log), and
[exact experimental patch](evidence/2026-09-26-vm-first/disk-backed-probe.patch).
The patch formats the disposable scratch disk in the isolated probe VM.
It is not a production initializer. It stops before a target image install.
This establishes B's device/network/storage prerequisites, not a complete desktop or a speed advantage.

## Experiment 3: Windows hypervisor prerequisites

A dedicated Corral/KubeVirt clone isolates the experiment from the native E2E fixture.
Windows could see virtualization and second-level address translation in the initial CPU probes.
The clone has 4 virtual CPUs and 12 GiB RAM; this is not an older-PC performance sample.

Windows reported the HypervisorPlatform feature disabled.
The command to enable it returned `RestartNeeded=True`.
Thus first use can need a Windows restart even though Linux preparation stays inside Windows.
The UI must distinguish this prerequisite from a reboot into the native deployer.

Checksums matched for the pinned QEMU package and firmware inside the Windows guest.
Nested acceleration still needs a probe that executes a guest.
A minimal Linux kernel can isolate that test from desktop image assembly.
Such a probe cannot establish a usable desktop or shared-disk migration.

## Compare B and C with the same workload

Use the same image digest, account inputs, target capacity, and clean Windows snapshot.
Separate cold-download runs from warm-cache runs. Repeat each condition three times.
Record interruptions and failed runs; do not average them away.

| Axis | Required observations |
|---|---|
| User effort | Prompts, administrator actions, Windows restarts, manual recovery steps |
| Time | Download, preparation, first desktop, later launch, native promotion; median and range |
| Resources | Host and guest peak memory, per-volume bytes, scratch peak, CPU time, idle footprint |
| Data | Selected files visible; copied/shared distinction; app setting and new file survive restart and promotion |
| Recovery | Download interruption, host restart, low disk, guest crash, cancel, repeated launch |
| Safety | No host Linux boot entry during VM setup; no simultaneous image writers; no raw host-NTFS passthrough |
| Experience | Readable progress, clear wait reason, keyboard access, low resolution, reduced motion |
| Offline | Complete bundle works without network; missing assets produce a useful blocked reason |

Test 4/8 GiB host-memory cohorts and rotational storage on actual hardware.
These results need more than a server VM with 12 GiB.
If the hardware cannot offer a useful guest, explain that and let the person choose a native path.
Do not silently use software emulation and label the result a normal desktop experience.

## Release decision

Prefer C only after it wins first-run effort/time without loss of safety or continuity.
Keep B if reuse of OCI data with verified hashes reduces download/storage costs or enables custom images.
Do not add a wizard choice for this implementation detail by default.
The distro profile selects the supported preparation backend; the user chooses the distro and data.

Both need a trusted artifact origin, digest/signature checks, scoped first-user setup,
private channels for VM control, recovery, and a proven path to native boot.
The current unsigned-manifest issue #371 also applies to any new prebuilt image.
These measurements do not establish a green Phase-1 result in the matrix.
