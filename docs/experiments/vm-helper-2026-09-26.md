# Disk-backed VM helper, 2026-09-26

This is a test of candidate B from the [VM-first experiments](vm-first-2026-09-26.md).
The helper provisions a raw disk without a host partition as input.
Desktop readiness is a separate gate from provisioner success.
These isolated tests do not mark a cell green in the hosted matrix.

## Rig and inputs

The test runs QEMU with KVM inside a dedicated Kubernetes pod.
The pod has its own PVC, no host volumes, and no Windows disks.
The helper has two CPUs and two raw disks with sparse allocation, each with 40 GiB capacity.
The target and scratch have distinct serials for VirtIO.
Network uses QEMU user-mode NAT and DHCP.

The first successful helper uses commit `4f9985d` and Alpine 3.21.
Its SHA-256 hashes are:

```text

builder-initramfs.img
```

Target: `ghcr.io/projectbluefin/bluefin@sha256:d3dd014e5ae0a46c0ca50e498ec20f18e6331e855e8d7fc3a70f52b4758e158b`.
Guest RAM: 3 GiB.

## Observations

Two failed runs exposed defects in the helper. Each emitted an error and shut down without success:

- crun could not use `pivot_root` from the initramfs root. The helper now uses `no_pivot_root`.
- bootc could not inspect `/run/udev`. The helper now starts eudev and shares its device database with the container.

The next run pulled the image, installed the OS, verified its deployment and fallback EFI loader, and shut down.
Its terminal result binds the image, run, install, and UUID from the disk GPT.
[Serial output](evidence/2026-09-26-vm-helper/helper-serial.log) and
[IPC output](evidence/2026-09-26-vm-helper/helper-ipc.log) record the result.
The helper powered off at kernel uptime 519.49 seconds; QEMU exited zero.
This is one run, not a product-speed promise.

At completion, the allocated blocks occupied about 7.1 GiB for the target and 9.6 GiB for scratch.
These are final allocations, not measured peaks or required free-space limits.
Sparse capacity is not the same as host space in use.
This run does not prove a 32 GiB target or a 2 GiB RAM profile.

OVMF then booted the exact target disk without another install.
The guest reached Linux 6.12.0-233.el10.x86_64 and a [login console](evidence/2026-09-26-vm-helper/installed-login.png).
The initial setup from GNOME crashed in GJS with `ffi_arg_pos == ffi_argc` (5 versus 0).
The journal showed a GBM renderer; this was not evidence of absent graphics drivers.

An account-function test on that stopped disk created a regular user, a persistent home, and SELinux labels.
The guest showed the user in GDM and accepted its password.
The session then crashed in GNOME Shell with `g_log_set_writer_func() called multiple times`.
[Journal excerpt](evidence/2026-09-26-vm-helper/bluefin-session.txt) shows that authentication succeeded but the desktop failed.
This pinned Bluefin image has no usable-desktop pass from this rig.

The image's QEMU guest agent answers identity queries but disables guest-exec and file operations.
Tests must respect that policy. A refusal does not mean the agent is absent.

## Private account input and 2 GiB RAM

Target: `ghcr.io/tuna-os/yellowfin@sha256:ed95623a4943a75b5ea61edb914de5a9b6033c4fb2ddb9de60fa14d88861520d`.
The host supplied a test account through private QEMU fw_cfg, with the run and install identities.
No password or hash appears in the kernel command line, result, or retained evidence.

The first run completed bootc at 274 seconds with 2 GiB RAM.
It refused success because PID 1 lacked `/usr/sbin` in PATH and could not find the target useradd.
The helper now sets an explicit PATH. A unit test starts with a restricted PATH and catches this regression.

A fresh full run then passed at kernel uptime 280.33 seconds and exited zero.
It pulled the image, installed Linux, created and checked the account, verified EFI and root, and unmounted scratch.
The result names the account and actual GPT UUID before `STATUS=SUCCESS`.
[Serial](evidence/2026-09-26-vm-helper/yellowfin-helper-serial.log),
[IPC](evidence/2026-09-26-vm-helper/yellowfin-helper-ipc.log), and
[artifact hashes](evidence/2026-09-26-vm-helper/account-helper-build.json) preserve the evidence.

[Resource samples](evidence/2026-09-26-vm-helper/yellowfin-resources.json) at 15-second intervals show peaks of:

| Observable | Sampled peak |
|---|---:|
| Target allocated blocks | 4.05 GiB |
| Scratch allocated blocks | 5.85 GiB |
| QEMU resident memory, including host overhead | 2.11 GiB |

These sampled peaks can miss short spikes. They are not free-space limits for a product profile.
Both files had 40 GiB capacity; they did not reserve 80 GiB of physical storage.
The desktop boot used 3 GiB RAM, separate from the 2 GiB helper test.

The exact disk booted through OVMF, but GDM could not start GNOME Shell.
Its [journal](evidence/2026-09-26-vm-helper/yellowfin-session.txt) reports a missing `org.gnome.shell` settings schema.
[Read-only inspection](evidence/2026-09-26-vm-helper/yellowfin-schema-inspect.txt) found the compiled cache and GNOME Shell 50 RPM.
It found no schema XML for `org.gnome.shell`; the RPM file list has only an override for it.
The RPM requires `gnome-shell-common = 50.0-3.el10`, but that package is absent.
The native fisherman cache step cannot compile an absent XML file.
This is a failed desktop gate, not a usable session.
The VM responded to ACPI shutdown and QEMU exited zero.

## Remaining gates

Both tested images pass provision and EFI boot but fail the usable-desktop gate on this rig.
A supported image must pass actual login plus a user file and setting across shutdown and restart.
Native promotion of the same disk, Secure Boot, resume, updates, and Windows host integration need separate proofs.
No candidate is ready for casual users solely because the helper emitted success.
