# Disk-backed VM helper, 2026-09-26

This is a test of candidate B from the [VM-first experiments](vm-first-2026-09-26.md).
The helper provisions a raw disk without a host partition as input.
Desktop readiness is a separate gate from provisioner success.
These isolated tests do not mark a cell green in the hosted matrix.

## Rig and inputs

The test runs QEMU with KVM inside a dedicated Kubernetes pod.
The pod has its own PVC, no host volumes, and no Windows disks.
The helper has two CPUs and two raw disks with sparse allocation, each with 40 GiB capacity.
The target and scratch have distinct serials for VirtIO.
Network uses QEMU user-mode NAT and DHCP.

The first successful helper uses commit `4f9985d` and Alpine 3.21.
Its SHA-256 hashes are:

```text
builder-vmlinuz
1f4cee6c1a6fc184650cff5b0f8d996b1079d4b47ebdfe6daa1d267a4f86359b
builder-initramfs.img
638188390bfd04aa38340fb925228020429da70034f6b48e14eb4f0fa6382391
```

Target: `ghcr.io/projectbluefin/bluefin@sha256:d3dd014e5ae0a46c0ca50e498ec20f18e6331e855e8d7fc3a70f52b4758e158b`.
Guest RAM: 3 GiB.

## Observations

Two failed runs exposed defects in the helper. Each emitted an error and shut down without success:

- crun could not use `pivot_root` from the initramfs root. The helper now uses `no_pivot_root`.
- bootc could not inspect `/run/udev`. The helper now starts eudev and shares its device database with the container.

The next run pulled the image, installed the OS, verified its deployment and fallback EFI loader, and shut down.
Its terminal result binds the image, run, install, and UUID from the disk GPT.
[Serial output](evidence/2026-09-26-vm-helper/helper-serial.log) and
[IPC output](evidence/2026-09-26-vm-helper/helper-ipc.log) record the result.
The helper powered off at kernel uptime 519.49 seconds; QEMU exited zero.
This is one run, not a product-speed promise.

At completion, the allocated blocks occupied about 7.1 GiB for the target and 9.6 GiB for scratch.
These are final allocations, not measured peaks or required free-space limits.
Sparse capacity is not the same as host space in use.
This run does not prove a 32 GiB target or a 2 GiB RAM profile.

OVMF then booted the exact target disk without another install.
The guest reached Linux 6.12.0-233.el10.x86_64 and a [login console](evidence/2026-09-26-vm-helper/installed-login.png).
The initial setup from GNOME crashed in GJS with `ffi_arg_pos == ffi_argc` (5 versus 0).
The journal showed a GBM renderer; this was not evidence of absent graphics drivers.

An account-function test on that stopped disk created a regular user, a persistent home, and SELinux labels.
The guest showed the user in GDM and accepted its password.
The session then crashed in GNOME Shell with `g_log_set_writer_func() called multiple times`.
[Journal excerpt](evidence/2026-09-26-vm-helper/bluefin-session.txt) shows that authentication succeeded but the desktop failed.
This pinned Bluefin image has no usable-desktop pass from this rig.

The image's QEMU guest agent answers identity queries but disables guest-exec and file operations.
Tests must respect that policy. A refusal does not mean the agent is absent.

## Private account input and 2 GiB RAM

Target: `ghcr.io/tuna-os/yellowfin@sha256:ed95623a4943a75b5ea61edb914de5a9b6033c4fb2ddb9de60fa14d88861520d`.
The host supplied a test account through private QEMU fw_cfg, with the run and install identities.
No password or hash appears in the kernel command line, result, or retained evidence.

The first run completed bootc at 274 seconds with 2 GiB RAM.
It refused success because PID 1 lacked `/usr/sbin` in PATH and could not find the target useradd.
The helper now sets an explicit PATH. A unit test starts with a restricted PATH and catches this regression.

A fresh full run then passed at kernel uptime 280.33 seconds and exited zero.
It pulled the image, installed Linux, created and checked the account, verified EFI and root, and unmounted scratch.
The result names the account and actual GPT UUID before `STATUS=SUCCESS`.
[Serial](evidence/2026-09-26-vm-helper/yellowfin-helper-serial.log),
[IPC](evidence/2026-09-26-vm-helper/yellowfin-helper-ipc.log), and
[artifact hashes](evidence/2026-09-26-vm-helper/account-helper-build.json) preserve the evidence.

[Resource samples](evidence/2026-09-26-vm-helper/yellowfin-resources.json) at 15-second intervals show peaks of:

| Observable | Sampled peak |
|---|---:|
| Target allocated blocks | 4.05 GiB |
| Scratch allocated blocks | 5.85 GiB |
| QEMU resident memory, including host overhead | 2.11 GiB |

These sampled peaks can miss short spikes. They are not free-space limits for a product profile.
Both files had 40 GiB capacity; they did not reserve 80 GiB of physical storage.
The desktop boot used 3 GiB RAM, separate from the 2 GiB helper test.

The exact disk booted through OVMF, but GDM could not start GNOME Shell.
Its [journal](evidence/2026-09-26-vm-helper/yellowfin-session.txt) reports a missing `org.gnome.shell` settings schema.
[Read-only inspection](evidence/2026-09-26-vm-helper/yellowfin-schema-inspect.txt) found the compiled cache and GNOME Shell 50 RPM.
It found no schema XML for `org.gnome.shell`; the RPM file list has only an override for it.

The RPM needs `gnome-shell-common = 50.0-3.el10`, but that package is absent.
The cache step in fisherman cannot compile an absent XML file.
This is a failed desktop gate, not a usable session.
The VM responded to ACPI shutdown and QEMU exited zero.

## Isolated image repair and persistence

A distinct image adds only the matching `gnome-shell-common` RPM to the pinned Yellowfin base.
The [Containerfile](evidence/2026-09-26-vm-helper/Containerfile.common-repair) checks the RPM hash and actual schema lookup.
[Provenance](evidence/2026-09-26-vm-helper/derived-image.json) records its immutable digest, package artifact, and hash of the local OCI archive.
The temporary [ttl.sh registry](https://ttl.sh/) holds only that public, neutral image, with a 24-hour tag.

It contains no test account, password, or private input. The helper pulls its digest over normal TLS.
This is an experiment, not a release image or a change to the default distro.

The unchanged helper installed that image and created the account in a fresh run with 2 GiB RAM.
It powered off at 286.27 seconds with the bound result and process exit zero.
[Serial](evidence/2026-09-26-vm-helper/derived-helper-serial.log) and
[IPC](evidence/2026-09-26-vm-helper/derived-helper-ipc.log) record the result.

The exact raw disk then passed a stronger gate on Linux KVM:

1. Enter the password for the account that the helper created.
2. Observe the [actual GNOME desktop](evidence/2026-09-26-vm-helper/derived-desktop.png) and open Ptyxis.
3. Confirm Linux and the username. Check that a test file is absent, then create it and change a setting.
4. Observe the [file and setting](evidence/2026-09-26-vm-helper/derived-before-restart.png), then request ACPI shutdown.
5. Relaunch the same raw disk, log in again, and [read both values](evidence/2026-09-26-vm-helper/derived-after-restart.png).
6. Shut down again. The supervisor records exit zero from QEMU. The GPT UUID still matches the helper receipt.

The [journal from the first session](evidence/2026-09-26-vm-helper/derived-first-session.txt) records login and poweroff.
The test file contains `phase1-76b8f1cb`; the setting is `org.gnome.desktop.interface color-scheme=prefer-dark`.
The second session only reads those values. It does not create or restore them.

[Exact desktop flags](evidence/2026-09-26-vm-helper/boot-installed.sh): Q35, KVM, host CPU, two CPUs, 3 GiB RAM, VirtIO block and network, virtio-vga.
OVMF boots the disk. Display output goes to HMP screenshots with no GL flag.
This does not prove Windows WHPX, the Windows bundle, its VGA defaults, or a 2 GiB desktop profile.
The image lacks QGA. Automated desktop readiness is not implemented; this proof uses a manual authenticated session.

An offline repair did not fix the booted OS.
Its chroot saw the new schema, but ostree composefs still served the original image at boot.
That result rejects a proxy: files under an offline deployment's `/usr` do not prove that the next boot will use them.
The successful test uses a new OCI image and a fresh install.

## Neutral disk archive experiment

A retained Yellowfin disk, without an account, serves as candidate C.
It uses the original image with the missing schema, so it is not a release candidate.
This experiment did not archive or publish a personalized disk.

[Measurements](evidence/2026-09-26-vm-helper/neutral-compression.json) come from one Linux pod run with two CPUs, low I/O priority, and other cluster work:

| Observable | Result |
|---|---:|
| Raw capacity | 40 GiB |
| Source allocated bytes | 4,362,088,448 |
| Archive with zstd 1.5.5, level 3, one thread | 1,939,724,807 bytes |
| Compression time | 50.01 seconds |
| Sparse restore plus file and directory fsync | 45.79 seconds |
| Restored allocated bytes | 6,459,318,272 |

Comparison of every byte returned zero. The UUID from the restored GPT matched the source.
The archive is about 8% larger than the original OCI payload of 1,793,371,955 bytes.
Despite sparse output, the restored file uses more blocks than the source.
Thus this format has no measured download or storage advantage.
It may reduce preparation work, but the timing excludes download, account creation, unique identity setup, and first boot.
It is not a Windows speed claim.

The [first restore failed](evidence/2026-09-26-vm-helper/neutral-restore-eviction.json) when the kubelet evicted the pod for low node storage.
The node eviction threshold was 23,502,050,623 bytes.
The successful retry used a 26 GiB infrastructure reserve after recovery and retained the failed result.
That shared-node reserve is separate from the proposed 8 GiB consumer reserve.
Cleanup removed the temporary copy only after comparison passed.

## Separate target and scratch capacity

The helper now declares and enforces independent minimums: 32 GiB target and 16 GiB scratch.
Legacy metadata retains 32 GiB as a conservative floor for both disks.
Both guards run before the first format. A test rejects each disk at one byte below its own minimum.
These are helper limits, not a promise that every image fits.
The Windows app still selects its existing capacities.

A fresh run used the same repaired image, private account input, two CPUs, and 2 GiB RAM.
[Artifact hashes and capacities](evidence/2026-09-26-vm-helper/capacity-16-build.json) bind this trial to source `fdd7fc9`.
The helper completed in 290.02 seconds of supervisor wall time and QEMU exited zero.
The [receipt](evidence/2026-09-26-vm-helper/capacity-16-helper-ipc.log) binds the created account and GPT UUID `3b6b7eba-ac83-4cf9-8ca2-34255e8d96bc`.
[Serial output](evidence/2026-09-26-vm-helper/capacity-16-helper-serial.log) records the full preparation.

[Samples](evidence/2026-09-26-vm-helper/capacity-16-resources.json) every five seconds show target allocation up to 4,419,760,128 bytes and scratch up to 7,355,285,504 bytes.
The node retained at least 32,037,679,104 free bytes, above the 26 GiB reserve.

The exact 32 GiB target then booted through OVMF with the same desktop flags and 3 GiB RAM.
After password login, the [actual desktop](evidence/2026-09-26-vm-helper/capacity-16-desktop.png) shows a terminal with `wootctest`, Linux, and system state `running`.
ACPI shutdown completed with QEMU exit zero. The GPT UUID still matched.
This trial does not repeat the earlier file-and-setting persistence test or prove Windows WHPX.

The [checks at boot](evidence/2026-09-26-vm-helper/capacity-16-installed-serial.log) reported a failure because system state was still `starting` inside the boot transaction.
After login, the user observed `running`. The evidence retains both observations.
Cleanup removed the stopped control disks after capture of evidence, to make room for the next experiment.
The earlier disk with the successful persistence test remains intact.

## Image-specific 8 GiB scratch experiment

A separate [experimental patch](evidence/2026-09-26-vm-helper/capacity-8-experiment.patch) lowers only its scratch minimum to 8 GiB.
It also requires the exact repaired Yellowfin reference before any storage writes.
The generic helper retains 16 GiB, and the app retains its current capacity selection.
A refusal test covers another image; boundary tests cover one byte below each disk minimum.
[Hashes](evidence/2026-09-26-vm-helper/capacity-8-build.json) identify the frozen experimental artifacts.
Their metadata retains the initial `unproven` label; the results here describe the later test, without a release approval.

The full fresh run with 32 GiB target, 8 GiB scratch, and 2 GiB RAM passed in 280.02 seconds.
It created and checked the account, verified root and EFI, unmounted scratch, and exited zero.
The [receipt](evidence/2026-09-26-vm-helper/capacity-8-helper-ipc.log) binds GPT UUID `1d59b644-fd6d-4566-8fc9-151562c0399b`.
[Serial output](evidence/2026-09-26-vm-helper/capacity-8-helper-serial.log) records the actual install.
Five-second [samples](evidence/2026-09-26-vm-helper/capacity-8-resources.json) reached 7,068,221,440 bytes for scratch and 4,410,318,848 for the target.
The least free space on the node was 32,237,588,480 bytes, above the 26 GiB reserve.

The exact target then booted with 3 GiB RAM and the same OVMF and graphics flags.
A password login reached the [actual GNOME desktop and terminal](evidence/2026-09-26-vm-helper/capacity-8-desktop.png).
The user observed Linux, `wootctest`, system state `running`, and 25,468,235,776 free bytes for writable `/var/home` and `/var` on the same filesystem.
This is about 23.72 GiB for user data and other mutable state.
It does not establish browser or app usability under memory pressure, or a 2 GiB desktop profile.
ACPI shutdown completed with QEMU exit zero and the same GPT UUID.
The [boot serial](evidence/2026-09-26-vm-helper/capacity-8-installed-serial.log) retains the separate early system-state check failure.
Cleanup removed the stopped trial disks after evidence capture. No test writer remains active.

This result supports a Windows experiment with 48 GiB admission: 32 GiB target, 8 GiB scratch, and 8 GiB consumer reserve.
It does not prove that Windows profile, future image versions, or another distro.
Host allocation samples do not measure the exact free space inside guest filesystems.
Production selection must bind a measured image profile to the exact signed runtime artifacts.

## Remaining gates

The helper component now has provision, account, EFI, desktop, and persistence evidence on Linux KVM with the corrected experimental image.
Original Bluefin and Yellowfin failures remain scoped to their tested configurations.
Windows WHPX and the full journey in the app remain unproven here. No cell changes in the hosted matrix.
